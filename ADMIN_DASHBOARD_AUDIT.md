# Synta Academy admin dashboard audit

Scope is the repository and synthetic local tests. No production data, provider operations, or production deployment were used.

## Report A — UX/UI implementation

The admin frontend uses vanilla HTML and JavaScript, page-local CSS, Tajawal or Inter, Font Awesome, a shared student stylesheet for the shell, and same-origin iframes. The admin shell has seven existing sidebar destinations. The settings placeholder is an additional direct-access page. Sign-in is separate. The unused head EJS fragment and legacy placement admin route were inspected separately from the dashboard iframe routes.

The shared styles live in `backend/public/admin/admin.css`. Static text and table header counts match the previous files. The overview contains an activity placeholder, with no chart instance, dataset, axes or tooltip implementation in the current admin source. KPI bindings and computations were preserved.

Headless Chrome visited eight iframe pages at 1440, 1024, 768 and 390 pixels. It found no document-level horizontal overflow or uncaught script exceptions in those runs. It exercised the mobile menu and Escape focus return, opened four existing dialogs on mobile, and separately verified payment modal Enter, Tab and Escape behavior. Synthetic HTTP responses supplied a KPI and payment row. External CDN fonts and scripts were excluded from the local fixture. No before/after screenshot comparison, real form mutation, or provider integration was performed.

All ten admin HTML inline scripts compiled. The regression suite passed 25 tests with one opt-in PostgreSQL scenario skipped. A separate test used the actual admin middleware with synthetic signed sessions and verified anonymous 401, student 403 and administrator access. No frontend build step is defined.

## Owner decisions

1. **Approve the unsafe rendering fix first?** Student values currently enter HTML in privileged views. Recommend safe text rendering and separate event binding, preserving the visible UI.
2. **Should the admin shell require server-side authorization, and should support impersonation remain?** Recommend aligning shell and API rules, retaining impersonation only if necessary, and making links one-time and auditable if retained.
3. **What should the overview count as active offers and revenue?** Recommend choosing the authoritative financial ledger and definition before changing figures. Confirm whether to retain the existing activity placeholder.
4. **Approve the payment status correction and existing API pagination/search in the page?** These improve review without adding financial mutation rights. Recommend leaving grant revocation and refunds restricted pending a separate workflow review.
5. **Should staff see placement answers and high-level course progress?** Recommend repairing existing placement details first, then approving only necessary read-only progress and expiry fields. Individual answers and learning history require tighter access.
6. **Should staff see signup and transaction events beyond the payment badge?** The API already assembles these events. Recommend keeping the current badge unless a specific operational need justifies broader event visibility.
7. **Is Bugi analytics intentionally private?** Recommend retaining the boundary for individual conversations and weakness records. If needed, consider aggregated usage with no raw conversations, code, or individual profiles.
8. **Should Settings stay developer-managed, and should admin actions have durable audit records?** Recommend keeping credentials out of the dashboard and separately reviewing schema migration and audit requirements before changing account deletion or financial operations.

## Approved follow-up

A01 was addressed in Students and Payments by serializing untrusted values from DOM text nodes and binding actions with event listeners. The touched Offers list and feature values use the same encoding. A04 now counts offers with is_active enabled. The Offers page lists both states and can toggle status through an admin-only endpoint.

The follow-up review found additional raw interpolation in placement registrant cells and answer details (`backend/public/admin/pages/free-session.html:381`, `:423`, `:427`), and an unescaped course thumbnail attribute (`backend/public/admin/pages/courses.html:835`). These paths were reviewed only and remain pending approval. The original table above records the audit before these approved fixes.
## Placement and thumbnail follow-up

The approved placement question, registration and answer renderers now encode text and bind controls through DOM listeners. The course table assigns validated thumbnail URLs to image elements and retains the existing placeholder on rejection or load failure. A local Chrome fixture confirmed both paths; the existing backend placement answer-data gap (A08) is separate and remains open.

Additional review findings, pending separate approval:

- The unused static head fragment has unescaped EJS values in JavaScript string literals (`backend/public/admin/pages/head.ejs:29`, `:35`–`:43`). Static delivery does not render these values. Do not reuse this fragment as an EJS view without safe serialization.
- Course chapter and live session action templates still interpolate database-generated UUIDs into inline event handlers (`backend/public/admin/pages/courses.html:940`, `backend/public/admin/pages/sessions.html:503`). This is a hardening opportunity. The audit did not establish a student-controlled path into those UUID fields.
